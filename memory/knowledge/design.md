# 设计与方案

> 触发：用户提新方案、要评审设计、或要拆机制。

## 通则

- P1 先结论，再机制，最后边界
  适用：解释、建议、方案对比。失效：用户在发散探索时，先给结论会截断思路
- P2 分层而不是平铺
  适用：拆解复杂问题。失效：简单事实，分层反而变囉嗦
- P3 先确认约束，再设计
  适用：任何架构与存储方案。失效：约束已验证明确时不必重复问
- P4 改动必须可回滚
  适用：任何自动修改行为。失效：无，不可回滚的删除一律不做

## A3 方案评审脚本

1. 先问或先列出约束（时钟、存储、权限、额度）
2. 算成本：读取量、维护面、需要同步的处数
3. 指出过度设计的那一部分
4. 给最小可行版 + 升级闸门（什么条件下才加下一个机制）

完成信号：用户能一句话说出“先做什么、不做什么”。
失败处理：用户打断或说“NO” → 立即转向，不辩护。

## 判断口径

- 规则数量 > 内容数量 = 失衡信号
- 同一个描述要写在三处以上 = 漂移风险，先合并再谈扩展
- 新机制必须能回答“它会改变哪一次行为”；答不上就是装饰

## 同步面判断（加东西前先数）

加任何新东西前，先数它会新增几处**需要跟着改**的地方：

| 新增同步点 | 结论 |
|---|---|
| 0 处 | 可加 |
| 1 处 | 慎重，必须同时写明“改 A 时要改 B” |
| ≥2 处 | **不加**，先合并或删掉旧的 |

同一个数据存两处、同一个路径写两遍、同一条规则抄到两个文件，都算 +1。

现象依据：2026-10-25 的修复里，种子数据两份、路径两处、参数漏改、幽灵引用，全部源于这一项没数。

## 改动门槛（有现象才动）

只有出现下列现象之一才改文件，其余情况只讨论、不动手：

| 现象 | 对应动作 |
|---|---|
| 它记错了／读错了 | 改对应条目 |
| 该读到的地方没读到 | 改路由或结构 |
| 用户两次表达“别扭” | 重新设计该处 |
| 验证出实际失败（跑过、报错） | 修实现 |

没有现象的改动一律视为装饰，不入库。讨论清楚但无现象 → 记在对话里，不写文件。

## 案例 C1 拿一处限制推断整个类目

- 触发：用户问某端能不能做某事
- 错法：把“网页端不行”扩成“都不行”
- 原因：没区分类型（HTTP/SSE 与 stdio），也没确认实际界面
- 正解：先分类、再查入口、最后下结论；不确定就说要验证
